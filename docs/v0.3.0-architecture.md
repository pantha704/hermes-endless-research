# hermes-endless-research — v0.3.0 Architecture: Persistent Campaign / Ephemeral Worker

**Status:** Design LOCKED for Phase 1 (implementation in progress). v0.2.16 remains the frozen
stable baseline. v0.3.0 is the deliberate capability line — do NOT tag v0.3.0 until the real
end-to-end supervisor + human review loop has passed.

---

## LOCKED architectural decisions (supersede any earlier draft)

1. **Supervisor core is one `research-runner`** with `--once` and `--loop`. `--loop`
   repeatedly calls the SAME `run_once()` implementation. A later systemd template simply runs
   `--loop`; there is no separate daemon logic.
2. **Review interface: CLI is authoritative.** Telegram becomes an adapter that calls the same
   state-transition API. Telegram never edits campaign files directly.
3. **Canonical state is ONE enum `campaign_state`:**
   `CONTINUE, BLOCKED, DORMANT, AWAITING_REVIEW, ACCEPTED, EXHAUSTED, PAUSED, ERROR`.
   There are NO two independently-writable `research_state` + `review_state` fields.
4. **RESEARCH_SUCCESS is an immutable audited EVENT** (a record in the run/audit journal),
   associated with the exact `objective_version` + `criteria_version` that passed. It is NOT a
   writable state. When `verify_success` passes, append a `RESEARCH_SUCCESS` event and
   atomically transition `campaign_state` → `AWAITING_REVIEW`.
5. **Active-file interface preserved:** `.research/objective.md` and `.research/criteria.jsonl`
   remain the live files the engine works with. Immutable snapshots live under
   `.research/versions/objective/v0001.md` and `.research/versions/criteria/v0001.jsonl`.
   `state.json` tracks `objective_version` and `criteria_version`.
6. **`refinements.jsonl`** records every human REFINE verbatim: timestamp, old/new objective
   version, old/new criteria version, resulting frontier additions.
7. **REFINE is one lock-protected logical transaction:** snapshot old objective/criteria →
   record user feedback → construct/write new version → update active objective.md/
   criteria.jsonl → add/activate new frontier work → change state to CONTINUE → append
   state/refinement audit event. NO historical objective, criteria, SUCCESS event, source,
   claim, edge, contradiction, checkpoint, or run-history entry may be rewritten.
8. **No systemd yet in Phase 1.** Phase 2 builds `research-runner`, validates one real Hermes
   one-shot worker with `--once`, then adds `--loop`, retry/backoff, session deadlines, profile
   creation, and finally a systemd template.
9. **Profile model (Phase 2):** a clean named `research-base`, then campaign profiles cloned
   from it (`--clone-from`, NOT `--clone-all`). Campaign profiles contain no unrelated
   conversational/session history.
10. **Versioning discipline:** keep v0.2.16 tagged and frozen. Commit Phase 1 in coherent,
    tested commits, but do NOT tag v0.3.0 until the end-to-end supervisor + human review loop
    has actually passed.

## Why this architecture

The v0.2.x line proves the engine's concurrency, lease, identifier, and audit-journal
subsystems. But its *execution model* is cron-driven: a calendar-bound scheduler fires a
session every N minutes, whether or not one is still needed. Cron is a scheduler; an
autonomous research campaign needs a **stateful worker orchestrator**.

The goal is not "run on a schedule" but "keep researching until the objective is
satisfied — and, crucially, until the *human* reviewing the result is satisfied." That
requires separating machine verifiable success from human acceptance, and versioning
objectives/criteria so iterating never rewrites history.

## Core model: Persistent Campaign / Ephemeral Worker

| Persistent (campaign-owned) | Ephemeral (per-session) |
|---|---|
| Objective (versioned) | Hermes session / context window |
| Criteria (`v1.json`, `v2.json`, …) | Reasoning trajectory |
| Evidence graph (edges, sources, claims) | Tool-call history |
| Frontier queue | Temporary hypotheses |
| Audit history (`run-history.jsonl`) | — |
| User refinements | — |

**Profiles isolate campaigns. Sessions perform bounded research. Disk carries knowledge.
A supervisor carries execution. The user owns final acceptance.**

## Separation of concerns

- **Supervisor** owns: lifecycle, time limits, retries, the campaign profile, session
  creation, journal-integrity checks, and whether to continue.
- **Hermes agent** owns: research, reasoning, tool usage, evidence generation, frontier
  decisions.
- A session **never decides whether another session exists**. It only writes state
  (`CONTINUE`, `next_action: CLUE-…`) and exits. The supervisor reads that and launches the
  next fresh session. This prevents recursive-agent recursion and gives one deterministic
  control plane.

## State machine (supersedes the old single "SUCCESS" terminal)

```
                     ┌─── CONTINUE
                     │
        research steps◄────┐ (criteria_version += 1, objective_version += 1 if needed)
                     │     │
                     └───► RESEARCH_SUCCESS  (deterministic machine criteria pass)
                                │
                                ▼
                         AWAITING_REVIEW    (paused: human examines result)
                                │
                    ┌───────────┴───────────┐
                    │                       │
                 ACCEPT                 REFINE
                 (done)             (human not satisfied)
                                        │
                                        ▼
                                   criteria v2
                                   CONTINUE ──► … ◄── (iterate)
```

Semantics:
- **RESEARCH_SUCCESS** — the deterministic, machine-verifiable success criteria currently pass.
- **AWAITING_REVIEW** — research is paused while the user examines the result.
- **ACCEPTED** — the user considers the campaign complete.
- **REFINE** — the user wants more; a new criteria/objective version is created, new frontier
  generated, and the campaign returns to CONTINUE. Nothing historical is rewritten.

## Versioned objectives & criteria (non-destructive iteration)

Active files stay where the engine already reads them; immutable snapshots are versioned:

```
.research/
  objective.md                 # ACTIVE objective (always v<current>)
  criteria.jsonl               # ACTIVE criteria (always v<current>)
  versions/
    objective/v0001.md
    objective/v0002.md
    criteria/v0001.jsonl
    criteria/v0002.jsonl
  refinements.jsonl            # verbatim human REFINE log (see below)
```

`state.json` tracks the active versions and the SINGLE canonical state:
```json
{
  "objective_version": 2,
  "criteria_version": 2,
  "campaign_state": "CONTINUE"
}
```

Each machine-verified SUCCESS is an **immutable RESEARCH_SUCCESS event** in the audit journal,
tagged with the exact `objective_version` + `criteria_version` that passed. The audit history
is a clean chain of *distinct* successes, e.g.: Objective v1 / Criteria v1 → RESEARCH_SUCCESS#1
→ user refines → Objective v2 / Criteria v2 → RESEARCH_SUCCESS#2 → user accepts → `ACCEPTED`.
Each SUCCESS is preserved and reproducible; nothing is rewritten.

## The supervisor

A single `research-runner` core with `--once` and `--loop` (one `run_once()` implementation):

```python
def run_once(campaign):
    state = load_campaign_state()
    if state.campaign_state in ("ACCEPTED", "DORMANT", "PAUSED", "ERROR", "EXHAUSTED"):
        return
    if state.campaign_state in ("AWAITING_REVIEW", "BLOCKED"):
        wait_for_user(); return
    run_id = create_run_id()
    launch("hermes", profile=campaign_profile,
           fresh_session=True, max_turns=150, prompt=campaign_tick_prompt)
    verify_checkpoint()
    verify_audit_chain()
    state = reload_state()
    if state.campaign_state == "CONTINUE":
        schedule_next_immediately()      # no artificial 30-min gap (in --loop)
    elif RESEARCH_SUCCESS_just_emitted():
        generate_report(); notify_user()  # state already atomically → AWAITING_REVIEW
```

Effect vs cron:
```
cron:  12:00 A |           12:30 B |           13:00 C |           13:30 D
supervisor:  12:00 A → 12:24 B → 12:49 C → 13:13 D → …   (tight back-to-back)
```

### Session budget (soft, not a hard 30-min wall)

- Soft research budget: 20–25 min
- Checkpoint / cleanup window: final ~5 min
- Hard supervisor deadline: ~30 min
- Combine with `--max-turns` (100–150) to bound the tool loop.

The session prompt should say: research aggressively until (1) the selected frontier branch
is resolved, (2) information gain becomes negligible, (3) you approach the session budget,
(4) you become blocked, or (5) the SUCCESS criteria are satisfied. Before ending: persist
every source/claim/edge, update the frontier, record contradictions/dead ends, write a
checkpoint, finish the audit run, and leave an explicit `next_action`. Then exit normally.

## Profile-per-campaign isolation (with a base profile)

Create a `research-base` profile configured once (web/browser/search tools, endless-research
skill, preferred model, max turns, research SOUL, API configuration), then clone per campaign:

```
hermes profile create research-base                    # once
hermes profile create research-jb-extension --clone-from research-base
```

Do NOT use `--clone-all` — you don't want the base profile's old sessions/state copied into
every campaign. Profiles isolate sessions, memory, config, skills, and identity/context, so
a jailbreak researcher never accumulates unrelated memory from another campaign.

## CLI surface (new shipped binary)

- `research-runner campaign-X` — start/ensure the supervisor for a campaign.
- `research-runner review campaign-X ACCEPT` — mark complete.
- `research-runner review campaign-X REFINE --criteria "…"` — return to CONTINUE with a new
  criteria version.
- `research-runner status campaign-X` — show campaign_state + objective/criteria versions.

## Cron's remaining role

Cron is not removed. It stays for *calendar-time* work:
- "Check this topic daily for new research"
- "Wake a DORMANT campaign next week"
- "Recheck a claim monthly"
- "Wait for an external dependency / paper / filing"

Two modes:
| Mode | Use |
|---|---|
| Continuous campaign runner | Research aggressively until success/acceptance |
| Cron / watcher | Research or recheck over calendar time |

## Phase plan (locked)

**Phase 1 — State-machine layer (THIS build, in progress).**
- Single `campaign_state` enum + RESEARCH_SUCCESS as an immutable audit event tied to
  objective_version + criteria_version.
- Active `objective.md` / `criteria.jsonl` preserved; immutable snapshots under
  `versions/objective/v0001.md`, `versions/criteria/v0001.jsonl`; `state.json` tracks the
  active versions and campaign_state.
- `refinements.jsonl` verbatim REFINE log.
- `review` subcommands: `ACCEPT` and `REFINE` (one lock-protected transaction) on the EXISTING
  CLI, fully tested. No systemd, no supervisor daemon yet.

**Phase 2 — `research-runner`.** One core `run_once()` with `--once` and `--loop`. Validate
one real Hermes one-shot worker with `--once`, then add `--loop`, retry/backoff, session
deadlines, profile-per-campaign (`research-base` + `--clone-from`, NOT `--clone-all`), and
journal-integrity checks — finally a systemd template running `--loop`.

**Phase 3 — Review UX + packaging.** Telegram as an adapter over the same review/state API
(never edits campaign files directly), docs, and the definitive end-to-end test: a real
campaign reaching RESEARCH_SUCCESS → AWAITING_REVIEW → ACCEPTED / REFINE.

## Phase 1 acceptance tests (from the decision spec)

- SUCCESS → AWAITING_REVIEW
- ACCEPT only from AWAITING_REVIEW
- REFINE only from AWAITING_REVIEW
- REFINE creates v2 while preserving v1 byte-for-byte
- previous SUCCESS remains tied to v1
- REFINE returns campaign to CONTINUE
- evidence (sources/claims/edges/contradictions/checkpoints) is preserved
- invalid state transitions fail closed
- concurrent/refused transitions do not partially modify versions
- current objective.md / criteria.jsonl remain compatible with existing engine commands

## Not addressed in Phase 1

- Multi-campaign supervisor resource budgeting.
- Backwards-compat for apps reading the old `current_state` field (kept as a derived/legacy
  field for the transition; not a new independent state).
- Whether REFINE may change the *objective* text or only strengthen criteria (Phase 1: REFINE
  accepts an optional new objective text; criteria are always carried forward + appended).
